<!-- sdlc:auto:start overview -->
Rag_chatbot_gemini_v8 is a two-part RAG (retrieval-augmented generation) chatbot application generated by the Quorq AI SDLC platform: a FastAPI backend (Python 3.12) that handles auth, chat sessions, PDF document upload/processing, and Gemini-powered Q&A with citations, and a React 19 + Vite SPA frontend that provides the approved UI screens. The backend persists users, sessions, documents, chunks, messages, and citations via SQLAlchemy models, defaulting to a local SQLite database (or Postgres with pgvector when DATABASE_URL is set), uses Alembic for schema migrations, RQ/Redis for background document processing, and Google's Gemini models for embeddings (gemini-embedding-001) and answer generation (gemini-2.5-flash). The frontend talks to the API via a typed fetch client and ships with Vitest unit tests and Playwright end-to-end tests.

<!-- sdlc:auto:start setup -->
1. Clone the repository.
2. Copy .env.example to .env and fill in required values (e.g. DATABASE_URL, Gemini/AWS credentials) as applicable.
3. cd backend && pip install -r requirements.txt
4. (Optional) docker-compose up -d to start local Postgres and Redis services defined in docker-compose.yml.
5. cd frontend && npm install
6. (Optional) cd frontend && npm run test:e2e:install to fetch the Playwright Chromium browser before running e2e tests.
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- One FastAPI router per architecture component (auth.py, sessions.py), included in app/main.py.
- Pydantic response schemas use `model_config = {"from_attributes": True}` and stringify UUID fields via field_validators before serialization.
- SQLAlchemy models use cross-dialect `sqlalchemy.Uuid` (not Postgres-only UUID) so the same models work against SQLite locally and Postgres+pgvector in production.
- Resource ownership is enforced via a shared `get_owned_or_404` helper and `get_current_user` dependency, scoping sessions/documents/messages to the authenticated user.
- JWT auth with a server-side revocation list (RevokedToken table keyed by jti) to give logout real effect despite stateless tokens.
- Passwords hashed with passlib[bcrypt] (pinned to bcrypt==4.0.1 for compatibility); minimum password complexity enforced server-side.
- Frontend screens are colocated with their Vitest test files (e.g. Sessions.tsx + Sessions.test.tsx); Playwright specs live separately under e2e/.
- Frontend API calls go through a single `apiFetch` wrapper (src/lib/api.ts) that attaches the bearer token, handles FormData vs JSON content-type, and force-redirects to /login on a 401 with an existing token.
- Protected frontend routes (/sessions, /sessions-sessionid) are gated by a `RequireAuth` route wrapper checking for a stored token.
<!-- sdlc:auto:end conventions -->

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| Backend fails to parse multipart file upload on POST /sessions/{id}/documents. | Ensure python-multipart is installed (it's in backend/requirements.txt); FastAPI only errors about this missing dependency at request time. |
| Frontend requests are blocked by CORS. | Make sure the backend's ALLOWED_ORIGINS (app/config.py, read from environment) includes the frontend's origin, e.g. the Vite dev server URL. |
| No database server available locally. | Leave DATABASE_URL unset; backend/app/database.py defaults to a local SQLite file (app.db) so the API runs end-to-end without Postgres. |
| Document upload/chat message generation returns 503/502 errors. | These indicate the Gemini API is not configured or the call failed (see app/routers/sessions.py); verify Gemini-related credentials/config are set. |
| Playwright e2e tests fail to start the backend. | playwright.config.ts expects a Python venv at backend/.venv with dependencies installed; install backend requirements into that venv before running `npm run test:e2e`, or set E2E_BASE_URL to point at an already-running deployment. |
| Logged-out token still appears to work. | Logout inserts the token's jti into the revoked_tokens table; confirm the same database is used by both the API process and worker, since revocation is checked via get_current_user against that table. |
<!-- sdlc:auto:end troubleshooting -->
